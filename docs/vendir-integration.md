# Native vendir delivery with Skills Auditor registration

Use vendir to materialize a pinned directory on each target filesystem. Then use Auditor's existing
plan/apply/verify interface to register its skills with the local agent. No vendir wrapper, new
package manifest, dependency solver, or second lock format is involved.

The [Potology example](../config/potology-vendir/vendir.yml) delivers the complete committed repository
at `9f1fd18022ecaaee14f8d2a67bf35821f48dc710`, using the
[native lock](../config/potology-vendir/vendir.lock.yml). Its
[Auditor config](../config/potology-vendir/skills-auditor.json) selects `task-handoff` and the external
Python modules, schemas, and documents used by that workflow. Skill-internal references are already
covered by the existing skill tree hash. The explicit file list is a reviewed acceptance scope,
not an automatic or universal proof of dependency completeness.

## Reproduce on a target

Prerequisites: vendir (tested with 0.46.3), this Auditor version, Git, and Potology's Linux/Python 3.12
runtime with SQLite FTS5. Source access must already be available through the target's authorized
transport. The application does not install runtime tools, provision credentials, or move secrets.

Copy the three example configuration files into a **new** deployment directory. Keep the directory
for as long as its registrations are in use. The example host is a separate `host/` subdirectory,
so the installed link cannot accidentally be confused with the source's own discovery location.

From that new deployment directory:

```sh
vendir sync --locked
python3 payload/tools/repo-context.py --help
python3 payload/tools/context_migration.py --help
skills-audit integrate --config skills-auditor.json --plan-out plan.json
```

Review `plan.json`, then apply and verify it:

```sh
skills-audit apply plan.json --receipt-out receipt.json
skills-audit verify receipt.json
```

For a real existing target project, override only the installation root when planning:

```sh
skills-audit integrate --config skills-auditor.json \
  --target-root codex=/absolute/target-project/.agents/skills --plan-out plan.json
```

Current Codex loads repository skills from `.agents/skills` and follows symlinked skill folders
([official documentation](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills)).
The legacy Auditor `--target codex` default remains `.codex/skills`; this recipe explicitly selects
the native location. Use the target runtime's convention, and test a fresh agent session after
registration. A successful Auditor receipt proves file and link state, not agent use.

Cross-filesystem transfer happens in vendir. Symlinks are only the final **local** registration,
pointing to content that already exists on the target. Do not transfer the source host's absolute
symlinks, plans, or receipts to another host; run integrate/apply there to produce its local bindings.
For transient/cloud environments, run the same steps during environment setup with persistent or
reconstructible delivery storage. The Linux container acceptance and subsequent dedicated GitHub
Codespaces experiment are separate evidence sets; see the [cloud report](../experiments/vendir-potology/CLOUD.md)
for tool-side visibility, recovery outcomes, and limitations.

## Updates and recovery

Prepare a new directory with the next reviewed native config and lock. Run native vendir, project
behavior checks, then generate a new Auditor plan against the same host root. Review and apply the
link replacement. Do not sync a directory already referenced by installed skills: that changes
live content before the integration plan is applied. Retain the previous directory and native lock
to restore its version and generate a fresh local registration plan.

Recovery still needs the pinned source objects. Do not use shallow Git depth for the tested historical
restore case: the earlier experiment demonstrated failure to fetch an old locked commit after the
source branch advanced. Native lock resolution, source retention, credentials, and download failures
remain vendir/transport concerns. There is no generic transactional rollback across hosts.

## Dependency acceptance and limits

`--require-file` (or `required_files`) captures bytes and permissions in the existing plan. Apply
rejects missing or changed dependencies before writing registration entries. Receipt verification
continues checking them, including files outside the skill directory. Config and native lock can
also be selected as ordinary required files; they are never parsed or regenerated by Auditor.

An upstream file omitted from this explicit list remains outside that check. Runtime binaries,
Python imports supplied by the environment, network services, semantic correctness, signatures,
and permissions to execute a workflow require their own checks. Auditor never executes commands
from an untrusted package as installation hooks.

The live [acceptance harness](../experiments/vendir-potology/agent_probe.py) runs native locked
delivery across filesystems, applies registration into a fresh host, deletes an external module as
a negative control, and invokes the target's existing Codex CLI in read-only ephemeral mode. It
asks the agent to discover `$task-handoff`, read its instructions/template, execute inventory and
retrieve an exact public Potology record. Inspect tool-call events and final output; process exit
alone is insufficient. The harness is a test fixture, not a production environment manager.

Private run evidence includes prompts and agent events. It is kept outside version control. The
probe cleans the temporary host and payload; its saved receipt describes a historical test, not
an installation left active. No source task is moved, no hook trust is changed, and no native
session restore or full task-handoff acceptance is claimed.

The live test exposed a useful distinction: delivery into `/dev/shm` passed Auditor verification
and appeared in the agent's catalog, but the agent's shell had a separate `/dev/shm` mount and could
not read the skill. Use storage visible inside the target tools' filesystem namespace. The corrected
probe uses the temporary host's overlay filesystem, distinct from the ext4 source. No relaxation
of the agent's isolation is necessary. The earlier two-container experiment separately verified
ext4-to-tmpfs locked restore; those are different acceptance claims.
